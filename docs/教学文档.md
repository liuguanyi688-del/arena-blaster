# 教学文档：从零搓一个浏览器 3D 肉鸽 FPS

> 本文档拆解 ARENA BLASTER 的完整技术实现，假设你会基础 JavaScript，
> 想学会：Three.js 游戏开发、FPS 手感系统、敌人 AI、肉鸽强化系统，
> 以及**真实项目里的坑是怎么踩和怎么填的**。所有代码可在本仓库对应文件中找到。

## 0. 项目能教会你的东西

- Three.js 游戏的**零构建**工程组织（不用 Webpack/Vite 也能做中型项目）
- FPS 三大件：**移动手感、射击判定、打击反馈**
- 敌人 AI 状态机与视线/避障
- 肉鸽强化系统的数据结构与生效链路
- 比功能更值钱的：**6 个真实线上事故的排查与修复**（见第 6 章）

## 1. 技术选型：为什么是"零构建"

| 方案 | 优点 | 缺点 |
|---|---|---|
| Unity / Godot | 功能全 | 产物重、学习成本高、Web 导出体积大 |
| Vite + Three.js | 工程化 | 需要构建链，对新手是额外噪音 |
| **原生 ES Modules + importmap** | 零构建、改完刷新即玩 | 需要自己管模块路径 |

我们选第三种。关键机制是 **importmap**（`index.html`）：把 `three` 等裸模块名映射到本地文件，
配合 import 语句的标准写法，效果等同打包工具的 alias，但没有任何构建步骤：

```html
<script type="importmap">
{ "imports": {
    "three": "./lib/three.module.js",
    "three/addons/loaders/FBXLoader.js": "./lib/addons/loaders/FBXLoader.js",
    "three/addons/utils/SkeletonUtils.js": "./lib/addons/utils/SkeletonUtils.js"
} }
</script>
```

**注意**：importmap 只解决"路径映射"，不解决"文件存在性"。FBXLoader 内部还会依赖
`NURBSUtils.js`、`BufferGeometryUtils.js` 等次级依赖——我们写了个脚本扫描所有
`from '...'` 相对导入并验证目标存在（踩坑实录 #6）。

├── level.js    (280行) 场景拼装 + 碰撞体 + 网格合并
├── weapon.js   (258行) 三武器：射击/换弹/切枪/强化消费
├── player.js   (215行) 移动/碰撞/视角/生命/冲刺/跳跃

## 3. 渲染循环与状态机（main.js）

```js
renderer.setAnimationLoop(() => {
  try {
    const dt = Math.min(clock.getDelta(), 0.05);   // 帧间隔，限幅防跳帧
    if (state === 'playing') {
      game.player.update(dt);                       // 物理+相机
      game.weapon.update(dt, input, targets());     // 射击+视图模型
      game.enemies.update(dt);                      // AI
      game.drops.update(dt, game.player, onPickup); // 掉落
      game.effects.update(dt);                      // 粒子
      updateHUD();                                  // DOM
    }
    renderer.render(scene, camera);
  } catch (e) {
    document.title = 'LOOP错误: ' + e.message;      // 远程可读的诊断（见踩坑#1）
  }
});
```

要点：
- **dt 限幅 0.05s**：切后台回来第一帧 dt 会巨大，不限幅会瞬移穿墙
- **状态机**：`boot/ready/playing/paused/dead/upgrade/win`，只有 playing/dead 推进世界
- **顺序即依赖**：玩家→武器→敌人→特效→HUD→渲染，物理先行保证本帧输入当帧生效
- **try/catch 包住整个循环**：任何异常写进 `document.title`，配合远程检查可以
  "不看屏幕也能知道哪行炸了"（本项目靠它抓到两个致命 bug）

## 4. 移动手感：加速度模型（player.js）

新手最容易写成"按键位移"（`pos.x += 5 * dt`），手感是瞬移。
正确做法是**速度向目标值渐变**（加速）+ 松键摩擦（减速）：

```js
const speed = sprint ? WALK_SPEED * 1.55 : (ads ? ADS_SPEED : WALK_SPEED);
this.vel.x += (wx * speed - this.vel.x) * Math.min(1, accel * dt);
this.vel.z += (wz * speed - this.vel.z) * Math.min(1, accel * dt);
this.vel.y -= GRAVITY * dt;                       // 重力
this.grounded = moveWithCollisions(pos, vel, dt, R, H, colliders);
```

`accel` 地面 14 / 空中 3——空中操控性 deliberately 变差，这就是"手感"。

### 4.1 碰撞：AABB 逐轴解算

不引入物理引擎，自己写 30 行：先动 X、再动 Z、最后动 Y，
每轴移动后检查玩家盒（0.36×1.78×0.36）与所有碰撞盒的重叠，重叠就推回并清零该轴速度：

```js
pos.x += vel.x * dt;
for (const c of overlaps(pos)) {
  if (vel.x > 0) pos.x = c.min.x - r - EPS; else if (vel.x < 0) pos.x = c.max.x + r + EPS;
  vel.x = 0;
}
// Z 轴同理；Y 轴额外处理"落到箱顶"和"撞头"
```

逐轴处理让"贴墙滑行"天然成立。地图碰撞体 = 每个建筑构件的 Box3，
在摆放时自动计算（`level.js` 的 `place()`）。

### 4.2 视角：Pointer Lock 的坑

- `mousemove.movementX/Y` 只有锁定时有效，切窗口立即失效——**必须在 UI 上告诉玩家**
- Esc 退出后有 **~1.25s 冷却**，期间 `requestPointerLock()` 静默失败——
  必须 catch 后延迟重试，并且**恢复游戏时才发起锁定**（见 main.js `tryLock()`）
- 姿态合成用 `rotateY(yaw) → rotateX(pitch) → rotateZ(roll)`，等价 YXZ 欧拉

## 5. 场景拼装：不量尺寸也能严丝合缝（level.js）

素材是几十个独立 GLB（墙、柱、地板……），尺寸/轴心未知。
核心技巧是 `place()` 函数——**放下去、量包围盒、再修正**：

```js
function place(key, cx, cz, { rotY, groundY = 0, scale = 1 } = {}) {
  const inst = templates[key].clone(true);
  if (scale !== 1) inst.scale.setScalar(scale);
  inst.position.set(cx, groundY, cz);
  group.add(inst); inst.updateMatrixWorld(true);
  const box = new THREE.Box3().setFromObject(inst);   // 量
  const c = box.getCenter(new THREE.Vector3());
  inst.position.x += cx - c.x;                        // 居中修正
  inst.position.y += groundY - box.min.y;             // 落地修正
  colliders.push(box.clone());                        // 碰撞体
}
```

用这个原语就能拼出：地板网格（双 for）、围墙环（按墙长分段）、城堡塔楼
（三段堆叠，`groundY` 递增）、跨包缩放建筑（`scale: 1.9`，碰撞盒自动跟随）。

### 5.1 性能：同材质合并

几百个构件 = 几百个 draw call。地板/墙共用同一材质，可以合并：

```js
for (const mesh of 同材质网格) {
  const g = mesh.geometry.clone();
  g.applyMatrix4(mesh.matrixWorld);   // 把世界变换烘进顶点
  geoms.push(g);
}
const merged = mergeGeometries(geoms, false);
```

代价是失去逐网格视锥剔除——对这种"全场景基本都看得到"的竞技场是纯赚。

## 6. 射击系统（weapon.js）

一次开火的完整链路：

```
input.fire → 冷却检查 → 弹药检查 → 生成方向(视线+散布锥) → Raycaster
→ 命中排序: [敌人碰撞盒/墙体] → 逐目标结算(穿透预算) → 曳光/火花/火光
→ 后坐力(视角上抬+枪模型后仰) → 散布(bloom)累加 → 音效
```

- **散布** = 基础(腰射/机瞄) + 移动附加 + 连发 bloom（每发+0.0075，随时间回落）
- **后坐力**：视角 pitch 上抬会自动回落一部分（`recoil -= recoil * 6 * dt`），
  枪模型用独立的 kick 值做后仰动画——**视觉和数值分开调，互不干扰**
- **穿透**：命中列表遍历，敌人命中数 ≤ `1 + pierce` 时继续处理下一个命中点，墙体直接截断
- **暴击/爆头**：碰撞盒带 `userData.head`，爆头固定 100（秒杀），暴击 ×2

### 6.1 关键决策：隐形碰撞盒（enemy.js）

骨骼动画网格（SkinnedMesh）的射线检测依赖骨骼变换，实测不可靠。
所以每个敌人挂两个**不可见的 Box**（身体 0.6×1.3×0.45 + 头 0.34³），
射线只打盒子。Three.js 的 Raycaster 不跳过 `visible=false` 的网格，正好利用：

```js
m.visible = false;                 // 看不见
m.userData.enemyRef = this;        // 命中后能找到敌人
m.userData.head = true;            // 爆头标记
```

这也是 CS/多数射击游戏的做法：渲染模型和判定体积分离。

## 7. 敌人 AI：最小可行的状态机（enemy.js)

```
PATROL ──视线发现(22m射线+遮挡)──▶ CHASE ──距离<17m──▶ ATTACK
   ▲                                │                    │
   └──────失去目标5秒────────────────┴─────拉出攻击圈────────┘
```

- **视线检测**：从敌人眼睛到玩家眼睛打一条射线，只和"墙体/道具"相交检测——
  被挡住 = 看不见。这就是所有射击游戏 AI 视觉的本质
- **攻击态**：不站桩——垂直于玩家方向横移拉扯（strafe），间歇性 3 连发点射
- **避障**：移动前向面前 1.3m 打一条短射线，堵了就随机转 70°（每 0.12s 才探测一次，省 CPU）
- **个体差异**：每个敌人速度 ×0.88~1.18 随机——四个敌人不再排队送死

程序动画补足：没被动画覆盖的动作（开火后坐颤动、死亡倒地）直接代码改
`model.rotation/position`——**"没有动作就合理做动作"**，比缺动作强。

## 8. 动画：FBX + AnimationMixer

- 角色模型与动画是**分开的 FBX 文件**（Kenney 的组织方式），
  加载动画文件后取 `animations[0]`，用 `AnimationMixer.clipAction(clip)` 绑定
- 状态切换用 `fadeIn/fadeOut(0.18)` 交叉淡化，避免姿势跳变
- **T-pose 排查**：动画没生效通常是轨道名和骨骼名对不上——
  我们写了"后缀模糊匹配"重映射兜底（enemy.js 管理器构造处），并暴露
  `mixer.time` 到调试条确认动画确实在跑

## 9. 打击反馈：一次命中发生什么

```
射线命中碰撞盒
→ hitmarker(CSS动画, 击杀变红变大)
→ 伤害飘字(DOM, 世界坐标.project(camera)投到屏幕)
→ 敌人材质 emissive 红闪 0.14s
→ 命中点火花粒子
→ 命中音效(随机音高防重复感)
→ 若致死: 倒地程序动画 + 烟雾 + 淡出 + 掉落判定 + 击杀播报
```

打击感 = **多个通道同时反馈**。只改数字不给反馈，玩家永远觉得"枪不行"。

## 10. 肉鸽强化系统（upgrades.js）

数据驱动的三层结构：

1. **runMods**：一个普通对象，存所有局内乘区（`dmgMult/rpmMult/critChance/pierce...`）
2. **UPGRADES**：每张卡是一个 `{ id, rarity, max, apply(mods, ctx) }`——
   `apply` 直接改 runMods 或玩家属性，**生效逻辑就地写在卡上**，加新卡零侵入
3. **消费方**：武器每次开火读 `runMods.dmgMult`，玩家移动读 `moveMult`……

抽取按稀有度加权（常见 60/稀有 32/史诗 8），过滤已达上限和前置不满足的卡。
选卡界面用键盘 1/2/3 触发——**保持指针锁定不弹鼠标**，交互一致性比点击更重要。

**流程调度一律帧驱动**：波间延迟、开波倒计时都是主循环里 `timer -= dt` 的游戏时间，
绝不用 `setTimeout`——后台标签页冻结时 setTimeout 永不触发，切回来流程就断了
（踩坑实录 #5）。

## 11. 特效与性能（effects.js + level.js）

- **光源池**：场景常驻 6 个 PointLight，开火时"借用"一个调亮度，用完归零。
  绝不 add/remove 光源——Three.js 光源数量变化会**重编译所有着色器**，每次开火卡 0.1~0.3s
- **粒子三件套**：曳光（拉伸圆柱+加法混合）、火花（Points+重力）、烟雾（Sprite+放大淡出）
- **自适应分辨率**：每 0.5s 统计帧率，<45fps 降 pixelRatio、>58 恢复——低端机保帧率的兜底

## 12. 踩坑实录（真实事故复盘）

|#| 现象 | 根因 | 修复 | 教训 |
|---|---|---|---|---|
|1| 打到东西画面就冻结，只有 CSS 动效还在动 | `this.sparks = []` 属性**遮蔽**了同名方法 `sparks()`，每帧 TypeError 中断渲染 | 属性改名 `_sparks` | 循环里任何未捕获异常=整帧跳过；主循环必须 try/catch 并把错误暴露到可观测处 |

## 13. AI 结对开发工作流（本项目的方法论）

这个项目由 AI（ZCode）主导开发与调试，人类负责需求与试玩反馈。可复用的做法：

1. **把游戏状态暴露成可观测接口**：`?debug=1` 时把 state/血量/弹药/异常写进
   `document.title` 和屏幕调试条——AI 通过窗口标题就能"看见"游戏内部，不用人肉截图描述
2. **自测模式**：`?autotest=1` 自动开局、瞄准、射击、送死、重生，全流程结果写标题，
   一次运行验证整条链路（还顺带发现"自动锁头"很好玩）
3. **回归自测**：每次大改后跑一遍 8 项检查（启/移/中/杀/死/生/命中探针/循环异常）
4. **错误进标题**：主循环 try/catch 把异常消息+栈首行写进标题，远程定位不用开 DevTools
5. **数值探针**：怀疑射击不生效时，把"每枪命中数/命中类型"也写进标题，直接排除法定位
6. **人在环**：AI 验证逻辑，人类验证手感——两边信息互补，缺一不可

## 16. V2 更新实战（这些系统已在仓库实现）

V2 把第 15 章的练习题做掉了一大半，实现思路存档：

- **霰弹枪多弹丸**（weapon.js）：cfg.pellets 存在时，主弹道之外按扇形角度补发
  N-1 条 fireRay()，每颗独立判定/曳光/伤害数字——六发全中的近战秒杀手感
- **BOSS 战**（enemy.js）：ENEMY_TYPES.boss（9 倍血、2.1 倍体型）+ isBoss 行为分支：
  攻击改为 5 发扇形弹幕（shootRadial 按绕 Y 轴旋转弹道），每 6~8 秒朝玩家冲撞（接触伤害）
- **全局攻击名额**：sharedAttack = { attackers: 0, maxAttackers: 2 }——最多 2 名敌人
  同时开火。这是"被群殴秒杀"问题的正解：不是削弱每个人，而是限制同时开火的人数
- **hit-stop 慢动作**：主循环用 effDt = dt * timeScale 更新世界；重kill时
  hitStop(0.15~0.5s, 0.22~0.35)——打击感的最后一块拼图，成本只有三行
- **新手引导**：帧驱动时间轴（TUTORIAL_STEPS 数组 + 游戏时间累加），后台冻结时引导
  也会暂停，回来无缝继续
- **战绩页**：跨局统计走 localStorage（总击杀/场次/最佳波数），主菜单可查

注意所有"延时后做 X"的游戏流程逻辑都走帧驱动而非 setTimeout——理由见踩坑 #8。
